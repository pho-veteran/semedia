Tài liệu Hệ thống Semedia

Snapshot tính đến 2026-06-03 (live stack + audit mã nguồn)

1. Overview

Semedia là hệ thống search media ngữ nghĩa cục bộ cho phép search bằng ngôn ngữ tự nhiên trên hình ảnh và video. Hệ thống chạy dưới dạng một stack Docker Compose khép kín gồm 5 dịch vụ, kết hợp CLIP visual-language embedding với keyword search TF-IDF để truy xuất và ranking kết hợp (hybrid). Tính đến lần chạy live verification ngày 2026-06-03, stack khởi động bằng Docker Compose, gateway báo cáo tính sẵn sàng của CUDA runtime thông qua media worker, và baseline benchmark đã ghi nhận được chấp nhận vẫn là phase12-e5-c1.

Các tính năng chính

  • 5 dịch vụ Docker — gateway API, media worker (GPU), search API, PostgreSQL database, React frontend
  • Hybrid search — CLIP vector similarity kết hợp với TF-IDF keyword matching để truy xuất hiệu quả
  • Hiểu video — tự động scene detection, captioning theo từng scene, multi-frame embedding
  • React frontend — giao diện hiện đại cho upload, duyệt thư viện và semantic search với kết quả thời gian thực
  • Evaluation framework — 120 judged query với tính toán metric tự động và so sánh với baseline

Nguyên tắc thiết kế

  • Local-first — mọi quá trình xử lý đều diễn ra trên thiết bị; không gọi API bên ngoài để thực hiện inference
  • GPU-accelerated — PyTorch hỗ trợ CUDA để sinh caption và embedding nhanh chóng
  • Modular services — mỗi dịch vụ có một nhiệm vụ duy nhất và giao tiếp qua HTTP
  • Shared logic — các model chung, mã nguồn pipeline và search helper nằm trong một shared Python package

2. Architecture

Semedia bao gồm 5 dịch vụ Docker giao tiếp qua một mạng nội bộ, cùng với một shared Python package cung cấp các model và logic chung.

Kiến trúc tuân theo mô hình microservice trong đó mỗi dịch vụ quản lý một domain cụ thể: gateway xử lý giao tiếp bên ngoài, media worker đảm nhận các tác vụ ML chuyên sâu trên GPU, và search API chịu trách nhiệm về logic truy xuất. Sự phân tách này cho phép scaling độc lập và phát triển riêng biệt từng thành phần.

  • Search API → Media Worker — HTTP nội bộ (embed query text/image)
  • Tất cả dịch vụ → DB — PostgreSQL qua SQLAlchemy (connection pooling)
  • Phục vụ Frontend — nginx phục vụ bản build React tĩnh, proxy /api/ sang gateway

3. Data Flows

Semedia có ba luồng dữ liệu chính: upload/processing (luồng ghi), text search (luồng đọc), và image search (luồng đọc trực quan). Mỗi luồng đi qua nhiều dịch vụ với ranh giới trách nhiệm rõ ràng.

a) Luồng Upload & Processing

Khi người dùng upload media qua frontend, file được nhận bởi gateway API, lưu vào đĩa và database, đồng thời một dòng MediaItem được tạo với trạng thái pending/enqueued. Gateway sau đó trả về mã 201 ngay lập tức và lập lịch một FastAPI background task để gọi media worker qua HTTP nội bộ. Bản thân pipeline của worker vẫn chạy đồng bộ khi được gọi — scene detection, captioning, embedding, và rebuild index hoàn thành ngay trong request của worker — nhưng phản hồi xác nhận upload là bất đồng bộ (asynchronous) từ góc nhìn của người dùng.

b) Luồng Text Search

Các query văn bản được embed bởi media worker thông qua endpoint /embed-text, tạo ra một vector CLIP 512 chiều. Search API sau đó thực hiện song song hai kênh truy xuất: vector search (độ tương đồng cosine đã hiệu chuẩn - calibrated cosine similarity - đối với tất cả embedding đã lưu) và keyword search (TF-IDF cosine đối với corpus caption). Kết quả từ cả hai kênh được gộp lại, tính score qua weighted fusion, rerank bằng các tín hiệu bonus, và lọc để đảm bảo tính đa dạng trước khi trả về frontend.

c) Luồng Image Search

Các query hình ảnh được embed qua /embed-image trên media worker, sau đó được đối chiếu dạng vector-only (không có kênh keyword) trước khi ranking. Điều này kích hoạt tính năng "tìm hình ảnh tương đồng" — người dùng có thể upload hoặc chọn một hình ảnh tham chiếu và tìm các media có nội dung hình ảnh tương tự. Vì không có query văn bản, kênh keyword hoàn toàn bị bỏ qua và trọng số fusion cho kênh vector thực tế là 1.0.

5. Data Model

Schema database bao gồm bốn bảng chính được quản lý thông qua các SQLAlchemy model trong shared package. Tất cả model đều sử dụng khóa chính kiểu số nguyên tự tăng và được truy cập thông qua interface Session đồng bộ của SQLAlchemy 2 trong các dịch vụ hiện tại.

Các embedding được lưu trữ dưới dạng mảng JSONB (danh sách float) thay vì một kiểu dữ liệu vector chuyên dụng, giúp hệ thống đơn giản và thuần PostgreSQL mà không cần các extension như pgvector. Việc này đánh đổi hiệu năng query khi hệ thống mở rộng để lấy sự đơn giản ở quy mô demo.

6. Processing Pipeline

Media worker xử lý mỗi file được upload thông qua một pipeline xác định (deterministic). Toàn bộ pipeline chạy đồng bộ trong một request duy nhất đến media worker.

Bước 1: Lưu trữ file

File được upload được lưu vào MEDIA_ROOT với một đường dẫn duy nhất được tạo từ UUID. Một bản ghi MediaItem được tạo trong database với status=pending kèm theo metadata enqueue, và gateway lập lịch gửi ngầm (background dispatch) tới media worker. Tên file gốc được giữ lại để hiển thị.

Bước 2: Scene Detection (Chỉ dành cho Video)

Đối với các file video, PySceneDetect chạy tính năng phát hiện nội dung thích ứng (adaptive content detection) với threshold cơ bản là 27.0. Thao tác này chia video thành các scene khác biệt về mặt ngữ nghĩa dựa trên sự thay đổi nội dung hình ảnh. Đối với mỗi scene được phát hiện:

  • Một keyframe đại diện được trích xuất tại thời điểm giữa scene
  • Một thumbnail nhỏ hơn được sinh ra để hiển thị trên giao diện
  • N=3 frame được lấy mẫu đồng đều trên toàn bộ thời lượng scene để thực hiện multi-frame embedding
  • Một bản ghi VideoScene được tạo liên kết ngược lại với MediaItem cha

Bước 3: Captioning

BLIP-large (Salesforce/blip-image-captioning-large) sinh ra caption bằng ngôn ngữ tự nhiên cho mỗi hình ảnh hoặc keyframe của scene. Pipeline bao gồm bộ lọc caption yếu (weak-caption filtering): nếu caption sinh ra quá ngắn, quá chung chung hoặc bị lặp lại, nó sẽ bị loại bỏ và sinh lại với các tham số beam search được điều chỉnh.

Bước 4: CLIP Embedding

openai/clip-vit-base-patch16 mã hóa mỗi hình ảnh hoặc keyframe thành một vector embedding 512 chiều được lưu trữ dưới dạng JSONB. Đối với các scene video, embedding của N=3 frame được lấy mẫu sẽ được tính toán riêng biệt rồi tính trung bình (mean-pooled) thành một embedding đại diện duy nhất cho scene, giúp nắm bắt sự biến đổi theo thời gian trong scene đó.

Bước 5: Rebuild Keyword Index

Sau khi xử lý, keyword index TF-IDF được rebuild từ đầu bằng cách sử dụng tất cả các caption trong database. Cấu hình:

  • scikit-learn TfidfVectorizer
  • Unigrams + bigrams (ngram_range=(1,2))
  • Tối đa 10.000 feature
  • Loại bỏ stop word tiếng Anh
  • Artifact đã serialize được lưu trong bảng KeywordIndexArtifact

Bước 6: Hoàn thành (Completion)

Trạng thái MediaItem.status được đặt thành completed. Item (và tất cả các scene của nó, đối với video) hiện đã có thể search đầy đủ thông qua cả kênh vector và kênh keyword.

7. Search & Ranking

Kênh Vector

Query văn bản được embed qua CLIP vào cùng không gian 512 chiều với các embedding của media đã được lưu trữ. Độ tương đồng cosine (cosine similarity) được tính toán giữa vector query và từng embedding đã lưu (hình ảnh + scene video). Các raw CLIP cosine score thường nằm trong một khoảng hẹp — theo thực nghiệm là [0.15, 0.40] cho corpus này — vì vậy một phép hiệu chuẩn affine (affine calibration) sẽ ánh xạ khoảng này một cách tuyến tính về [0, 1]:

calibrated = (raw_cosine - 0.15) / (0.40 - 0.15)
calibrated = clamp(calibrated, 0.0, 1.0)

Điều này đảm bảo vector score sử dụng toàn bộ phạm vi [0, 1] và có độ lớn tương đương với keyword score để phục vụ quá trình fusion.

Kênh Keyword

Query được vector hóa bằng cách sử dụng cùng từ vựng TF-IDF với corpus caption đã được lưu trữ. Độ tương đồng cosine được tính toán giữa vector TF-IDF của query và từng vector tài liệu (caption) trong index. Kênh này cực kỳ hiệu quả trong việc khớp chính xác các thuật ngữ (exact term matches) và các thực thể định danh cụ thể (named entities) mà CLIP có thể không nắm bắt tốt. Keyword score tự động nằm trong khoảng [0, 1] và không cần hiệu chuẩn.

Fusion

Base score cuối cùng kết hợp cả hai kênh với các trọng số được điều chỉnh theo thực nghiệm:

score = 0.7 × vector_score + 0.3 × keyword_score

Tỷ lệ chia 70/30 phản ánh việc CLIP embedding nắm bắt ý nghĩa ngữ nghĩa rộng hơn (khái niệm trực quan, mối quan hệ không gian, ý tưởng trừu tượng), trong khi TF-IDF vượt trội ở việc khớp các thuật ngữ cụ thể mà CLIP có thể bỏ lỡ. Các item chỉ xuất hiện ở một kênh sẽ nhận đóng góp bằng 0 từ kênh còn lại.

Các Reranking Bonus

Sau khi fusion, các bonus cộng thêm sẽ thưởng cho các tín hiệu văn bản mạnh mẽ biểu thị độ liên quan cao:

  • +0.08 — cụm từ query chính xác được tìm thấy trong caption (khớp chuỗi con không phân biệt chữ hoa chữ thường). Điều này thúc đẩy mạnh mẽ các item có caption mô tả trực tiếp những gì người dùng tìm kiếm.
  • +0.02 — rich caption (độ dài > 50 ký tự). Các caption dài hơn cho thấy hiểu biết scene mang tính mô tả nhiều hơn, chất lượng cao hơn, tương thích tốt hơn với CLIP alignment.

Các khoản bonus này mang tính cộng dồn và có thể đẩy score vượt quá 1.0 trước khi thực hiện clamp cuối cùng.

Đảm bảo tính đa dạng (Diversity Enforcement)

Để tránh việc một video duy nhất chiếm lĩnh kết quả với nhiều scene tương tự nhau:

  • Per-media cap — Tối đa 2 scene cho mỗi media item xuất hiện trong kết quả cuối cùng (có thể cấu hình qua SEARCH_MAX_PER_MEDIA)
  • Caption deduplication — Các kết quả có caption trùng nhau sẽ được thu gọn về instance có score cao nhất
  • Sắp xếp (Ordering) — Sau khi lọc đa dạng, các kết quả được sắp xếp lại theo final score giảm dần

Final Score

Sau khi fusion, reranking bonus, và lọc đa dạng, final score được clamp về [0, 1]. Các kết quả dưới mức SEARCH_MIN_SCORE (mặc định 0.0) sẽ bị loại trừ. Kết quả phản hồi bị giới hạn ở mức tối đa SEARCH_MAX_RESULTS (mặc định 20) item.

Một giai đoạn cross-encoder rerank tùy chọn có tồn tại (được kiểm soát bởi SEARCH_RERANK_ENABLED) nhưng bị disabled theo mặc định. Lịch sử benchmark hiện tại cho thấy bộ reranker chỉ dựa trên caption MS-MARCO được thử nghiệm làm giảm chất lượng trên corpus này vì nó loại bỏ tín hiệu trực quan của CLIP khi thay thế fusion score, vì thế nó vẫn là một tính năng lựa chọn thêm (opt-in) thay vì là luồng mặc định.

8. Hệ thống đánh giá (Evaluation System)

Semedia tích hợp sẵn một evaluation framework để đo lường chất lượng truy xuất so với một corpus bị khóa (locked corpus) gồm các judged query.

Corpus & Query

  • 120 judged query — 97 positive (mong đợi kết quả liên quan) + 23 negative (mong đợi không có kết quả)
  • Locked corpus gồm 35 asset — 28 hình ảnh + 7 video lấy nguồn từ Wikimedia Commons
  • Video-granularity scene credit: một scene video khớp với query được tính là một lượt hit
  • Các query bao phủ nhiều danh mục khác nhau: động vật, phong cảnh, đồ vật, hành động, khái niệm trừu tượng, màu sắc, bố cục
  • Các negative query dùng để kiểm tra tính đặc trưng (specificity): các query cho các đối tượng không có trong corpus phải trả về kết quả rỗng hoặc độ tin cậy cực kỳ thấp

Lượt chạy live ngày 2026-06-03 được thực hiện bằng lệnh docker compose --profile test run --rm service-tests python testing/evaluation/run_evaluation.py --base-url http://gateway-api:8000 --queries testing/evaluation/queries.json --compare-to testing/evaluation/baselines/baseline-phase7.json và trả về trạng thái so sánh ok. Baseline benchmark được ghi nhận chấp nhận trong lịch sử dự án vẫn là phase12-e5-c1 với P@10 0.1103, R@10 0.9794, MRR 0.8664, và NDCG@10 0.8902. Như đã lưu ý trong rubric, P@10 thấp là điều bình thường trên locked corpus nhỏ này và nên được diễn giải cùng với Recall/MRR/NDCG.

Các tính năng

  • Theo dõi false-positive cho negative query (các query không nên trả về kết quả gì)
  • So sánh baseline giữa các lượt chạy (báo cáo delta)
  • Tùy chọn xuất file report từ evaluation CLI
  • Tự động gieo dữ liệu (seeding) corpus từ testing/evaluation/assets/

Phương pháp luận (Methodology)

Mỗi query positive có một hoặc nhiều item liên quan dự kiến được xác định bằng tên file hoặc scene. Trình chạy đánh giá thực thi mỗi query đối với search API đang hoạt động, thu thập các kết quả top-K và tính toán metric cho từng query. Các metric tổng hợp chính chỉ được tính toán trên các query positive; các query negative đóng góp vào phần tóm tắt false-positive riêng biệt.

Các query video sử dụng video-granularity scene credit trong quá trình tính điểm: các khóa scene trong runtime được gộp về video cha, do đó việc truy xuất bất kỳ scene nào từ đúng video đều được tính điểm cho scene được gắn nhãn. Điều này khớp với benchmark rubric hiện tại và các quy tắc đo lường E5 đã được chấp nhận.

Lưu ý cấu hình

  • Lựa chọn model — CLIP_MODEL_NAME và CAPTION_MODEL_NAME chấp nhận bất kỳ mã định danh model nào từ Hugging Face. Việc thay đổi model yêu cầu xử lý lại (reprocess) toàn bộ media để sinh lại các embedding và caption.
  • Điều chỉnh search — Trọng số vector/keyword (0.7/0.3) đã được tinh chỉnh thực nghiệm trên evaluation corpus. Việc điều chỉnh các trọng số này ảnh hưởng đến toàn bộ kết quả search ngay lập tức mà không cần xử lý lại.
  • Cấu hình GPU — Cấu hình mặc định chung cho phép lựa chọn CUDA không bắt buộc (non-strict), nhưng stack Docker Compose đi kèm đặt ML_STRICT_CUDA=1. Lượt chạy live ngày 2026-06-03 báo cáo selected_device=cuda với một GPU NVIDIA hiển thị.
  • Preloading — ML_PRELOAD_MODELS=1 đang hoạt động trong stack hiện tại và làm tăng thời gian khởi động nhưng loại bỏ độ trễ cold-start ở request đầu tiên.
  • Scene detection — Giá trị SCENE_DETECTION_THRESHOLD thấp hơn sẽ tạo ra nhiều scene hơn (nhạy hơn với sự thay đổi); giá trị cao hơn tạo ra ít scene hơn và dài hơn.

Định hướng tương lai

  • Hàng đợi xử lý bất đồng bộ (Redis + Celery hoặc tương đương) để upload không bị nghẽn (non-blocking)
  • Tích hợp cơ sở dữ liệu vector (pgvector, Qdrant, hoặc Milvus) để mở rộng tính năng tìm kiếm approximate nearest-neighbor
  • Evaluation corpus lớn hơn để mở khóa phép đo P@10 có ý nghĩa và stress-test xếp hạng
  • Multi-GPU và batch inference để nâng cao throughput trên các thư viện media lớn
  • Cross-encoder reranking được tinh chỉnh cho các corpus lớn và đa dạng hơn nhằm thể hiện rõ giá trị
  • Vòng phản hồi của người dùng (user feedback loop) để học hỏi mức độ liên quan và ranking cá nhân hóa
  • Cập nhật keyword index lũy tiến (tránh rebuild toàn bộ mỗi lần upload)
  • Tối ưu hóa sinh thumbnail và lazy loading trong frontend
  • Phân tích luồng âm thanh cho video (speech-to-text, phát hiện sự kiện âm thanh)
  • Tối ưu hóa sinh thumbnail và định dạng WebP để dung lượng payload nhỏ hơn
  • Tiến độ xử lý thời gian thực qua WebSocket hoặc SSE
  • Hỗ trợ đa ngôn ngữ cho caption và search query
